Loot Overhaul — Design Notes

Status: draft plan, targeted at the Season 3 launch. It is built and tested phase by phase on the dev realm. The roadmap epic is loot-overhaul. This page supersedes the contraband/legality section of Slotted Items (Gem Socketing). The rest of that draft is adopted as Phase 5.

Context

What loot looks like today, and why it needs replacing.

Every drop in the module is a fixed, hand-placed blueprint item. Nothing rolls item properties, rarity or tiers.

  • Chests. About 500 chests (chest_respawner 188, chest_refilllow 167, chest_refillhigh 139) call the stock GenerateLow/Medium/HighTreasure from nw_o2_coninclude.nss. That code is scaled to the opener's hit dice and capped at 17, so at levels 40–60 it hands out junk. Rajmund's request (rng-based-gear-diablo-world-of-warcraft-style) calls it "garbage/stock items … from 99.5% of containers".
  • Bashable placeables run the stock nw_o2_class*/general* scripts.
  • Spawn treasure. The stock spawn-time path (CTG_GenerateNPCTreasure) is believed to produce nothing; this is inferred, not yet verified in game.
  • Bosses drop their fixed blueprint inventories.
  • Waiting on random loot: three backlog items. They are Socket-system-for-weapons (Methonash), optin-curse-gem-loot and season3-meta-shakeup.

Reference, not import. Commche's Random Loot Generation System v2.0 (2014, pre-EE, licence "open only if project also open") is a source of ideas:

  • quality bands by level;
  • coloured quality names;
  • up to 6 sockets;
  • class item sets.

Its code would clash with CEP, the forge and the module's persistence conventions, so none of it is imported.

Decisions (admin, 2026-11-05)

The shape of the system as agreed.

Loot modelMostly fully random, with hybrid elements. Random items get a rarity and affixes scaled to their source. The hand-made items stay: bosses keep their fixed drops, and curated obtainable items join a named pool that Legendary rolls can award.
ContainersEvery generic chest and container switches to random loot. Quest chests, the Setti coffers, the donation chest and books stay as they are.

WikiDocumented by nwn_manager from the same data the game reads. Classic-loot modules must render byte-identical, proven by the golden gate with the baseline recorded first.

Architecture

One data source for the game and the wiki, plus one runtime include.

Data: loot/*.json at the repo root

The folder sits next to unpacked/ and holds JSON only, because the wiki generator is pure stdlib with no YAML loader.

FileHolds
rarity.jsonCommon, Uncommon, Rare, Epic and Legendary. For each: name colour, affix-count range, value budget per loot level, socket-count range and drop weight.
levels.jsonCR → loot level 1–60, as clamped log-style bands (boss CRs reach 9,540), plus per-boss overrides.
bases.jsonBase-item categories (melee, ranged, armor, shield, jewelry, wearable, caster) with weights and appearance model pools. This is where the even spread of weapon types is tuned.
affixes.jsonEach affix: property type, subtype and cost range by loot level; allowed categories; weight; prefix/suffix name; role tags. All ids are validated against module-index/enums.json.
named.jsonThe hybrid pool: curated existing .uti resrefs, each with a loot-level window and rarity.
gems.json, sockets.jsonGems by rarity band, and the socket schema for existing items.
sources.jsonChest and placeable script → loot profile; creature classes (normal, elite, boss); boss table defaults and overrides; per-area loot-level overrides; exclusions.
tokens.jsonFate token sources and rates.

Generated include + build gate

bin/gen-loot-tables.py reads the JSON and writes unpacked/loot_data_inc.nss. It is committed and never hand-edited, the same pattern as bin/gen-forge-legal.py. The tables are compiled into the module rather than stored in a campaign DB, so the dev and live realms can never drift apart.

tests/check_loot_tables.py runs from tests/smoke-test and fails the repack on:

  • a stale include;
  • an unknown base-item row, iprp id or cost value;
  • a named resref that is missing or not obtainable;
  • a rarity whose value budget cannot be reached.

Runtime: loot_inc.nss

Loot_Roll(nLevel, nRarityFloor, sProfile, oBeneficiary, oDest) creates one item, in this order:

  1. Base. Pick a base item from the profile's category weights, biased by the beneficiary's wishlist. Create it from the existing forge_blank_<baseitem> blanks (ForgeBlankResRef). Randomize its appearance from the bases.json model pools.
  2. Rarity. Roll it, apply the floor, then a weighted one- or two-band upgrade.
  3. Affixes. Roll up to the rarity's count. Build each one with IPGetItemPropertyByID, not itemprocs, which depends on conversation locals. Same-type affixes merge rather than stack (see the bonus-ledger note).
  4. Budget. Check the value with ForgeItemValue / ForgeRebuildValue; never read it in place after a removal.
  5. Name. Coloured <Prefix> <Base> of <Suffix>. The word lists are prose, so the local LLM may draft them, with every write recorded in the ledger.
  6. Stamp. Write LOOT_VER, LOOT_LVL, LOOT_RARITY and LOOT_PROFILE, plus LOOT_AFX_N / LOOT_AFX_<i> holding one ForgePropSig per random affix.
  7. Named. A Legendary roll has a chance to create a named.json item instead.

Why the stamps matter. They live in the .bic and survive the party roll's CopyItem. They are what lets a Fate token remove exactly the random affixes, and never a forged enchantment or a socketed gem.

Test surface + simulator

Admin Options → Loot Lab is a rest-menu entry gated by Admin_CanAdmin; there is no DM console. It can:

  • roll N items at level L and rarity R;
  • re-stock the nearest chest;
  • grant gems and tokens;
  • dump an item's LOOT_* stamps.

bin/loot-sim.py runs Monte Carlo over the same JSON and prints, per loot level, drop rates, rarity mix, value percentiles and affix frequency. It is the balance check before any build, and it produces the odds tables the wiki shows.

Phases

One hidden roadmap item each, under the loot-overhaul epic, in build order.

1. Remove the contraband jail (lo-remove-jail)

This phase is independent of loot and can ship to dev now.

Before deleting anything: check the craftdb quarantine counts on the dev and S2 realms, check for any jail-flagged PCs, and confirm whether the prison, jailor and _homerjail areas and scripts serve anything besides the forge.

Delete:

  • ForgeJail*, the quarantine and the login scans (ForgeBeginScan and ForgeBeginWardenScan, called from mod_cliententer and welloferuenter);
  • forge_scan_step;
  • the whitelist: forge_legal_inc.nss and bin/gen-forge-legal.py;
  • the Forge Warden.

Keep the cap math used at purchase and in staged disenchant.

Add a one-shot login release for anyone still jailed, which hands back their quarantined items.

Also update: tests/check_forge_disenchant.py, and the contraband section of Customizations/Crafting.html, which is marked retired with its id kept. Fix the stale Rune "activate" text in the same edit. forge_inc is an include, so this needs a clean repack.

2. Loot core (lo-loot-core)

  • Golden gate first: run bin/wiki-golden baseline, then refactor the six copies of the generator's "item accessible" rule into one predicate. The check must show zero diff.
  • The pieces: the loot/ starter set (5 rarities, about 40 affixes, the level bands), the generator, the gate, loot_inc, Loot Lab, loot-sim, and the lootdb campaign DB with its DDL in onmoduleload.
  • Season 3 axes. Seed affixes on the axes season3-meta-shakeup names: Spell Resistance, amulet alternatives to the 25% physical-immunity answer, and caster magicstaff affixes. Avoid simply bigger attacks-per-round or divine damage.

3. Chests and containers (rng-based-gear-diablo-world-of-warcraft-style)

  • Area loot level. bin/gen-area-loot-levels.py derives each area's level from the median hostile CR. Chests roll at the area's level, so a high-level player gets nothing special from low-level chests.
  • Refill scripts. The refill call in chest_respawner, chest_refilllow, chest_refillhigh and chestrespawn* becomes Loot_Roll. Low, medium and high set the roll count and rarity floor. The 200-second refill timer stays.
  • Bash-open placeables. Local overrides of nw_o2_classlow, nw_o2_generallow, nw_o2_classmed, x2_02_low, x0_o2_any* and the rest put them on the same profiles.

4. Creature and boss drops (lo-creature-drops)

bst_ondeath (the universal death wrapper) calls loot_ondeath, which sets drop chance and roll count by creature class:

  • normal: low chance;
  • elite: CR well above the area's level;
  • boss: anything in the brd_db registry.

Excluded: associates and summons, PC-less kills, creatures with a LOOT_NONE local, and listed quest creatures.

Bosses keep their fixed drops and add, on top:

  • Epic-floor random rolls;
  • a chance at the named pool;
  • a gem;
  • a Fate token chance.

Everything lands on the corpse, where the Need/Greed roll handles it unchanged.

5. Sockets and gems (Socket-system-for-weapons)

Adopt the socket draft, minus its jail integration:

  • SOCKET_* item locals;
  • a generated socket_def_inc plus a version-stamped login reconcile for existing items;
  • gems activated onto a target item;
  • gem drops by CR band.

Additions:

  • Random items roll their socket count from their rarity.
  • A gem merges with a same-type property and never overwrites a forged one. It is clamped to Methonash's caps (2d10 damage, AB +16).
  • Sockets are separate from forge property slots.

6. Base-item wishlist (lo-wishlist)

  • Storage. lootdb wishlist(uuid, base_item), up to 5 picks per character.
  • UI. An NUI picker from the rest menu.
  • Effect. A P% chance (start at 40%) that a roll draws its base from the beneficiary's wishlist, within the profile's allowed categories. With no wishlist, "Auto" weights by the beneficiary's weapon-focus and proficiency feats.
  • Beneficiary. For a corpse, a random damage-contributing party member who is present; for a chest, the opener.
  • Known gap. Wishlists reset on dev, because the vault sync copies .bic files but not the realm DBs.

7. Fate token (lo-fate-token)

  • Reforge. A new anvil reply, "Reforge its fate", in all four smith dialogs, added via bin/inject_forge_disenchant.py and modelled on ForgeExpandDo. It consumes one token and re-rolls only the item's LOOT_AFX_* affixes at the same level and rarity. Sockets, gems and forged enchantments are untouched.
  • Boss bonus roll. At a boss death, each damage-contributing PC holding a token gets an NUI prompt with a 60-second timeout. If they accept, one boss-table roll goes straight into their pack. The limit is one per PC per kill, with the lockout in lootdb.

8. Wiki + player docs (lo-wiki)

nwn_manager loads <project>/loot/ only when it exists, which is the sibling-folder convention. With it, the wiki gains:

  • a fifth item-source table, item_from_loot, so named, gem and token items are no longer "inaccessible";
  • a Drops section on creature pages;
  • the loot profile on container pages, instead of "random treasure, cannot be listed";
  • generated pages: Loot overview, Affix catalogue, Gems & Sockets, Fate tokens;
  • a schema README for other modules.

Add loot to the golden gate's PROJECT_INPUTS. The archive modules (lotr2008 and lotr2009) must show zero diff.

Player docs. A new Customizations/Loot.html topic page with sections #loot-rarity, #loot-levels, #loot-chests, #loot-wishlist, #sockets, #gems and #fate-token, plus gen-customizations-hub.py. Each phase fills in its own section as it ships.

Follow-on, outside this epic optin-curse-gem-loot (in Difficulty Increase) becomes a rarity-floor bump for cursed players, a few lines on top of phases 4 and 5.

Open questions

Taste calls, tracked as design_questions on the epic's items.

  • Token name. Proposals: "Ithildin Core" or "Shard of Fate".
  • Token sources and rates. Proposal: a boss-drop chance, a merit shop entry, and a weekly cap on bonus rolls.
  • Wishlist size and bias. Proposal: 5 picks at 40%.
  • Rarity colours. Proposal: white, green, blue, purple, orange, to match WoW/Diablo convention.
  • Item sets (the CommChes idea). Proposal: park them for after Season 3 launches.
  • Gem extraction. Proposal: none; socketing is permanent, as the socket draft says.

Verification

How each phase is proven.

  • Phase 1.
    • A clean repack passes every gate.
    • The packed mod_cliententer.ncs no longer calls the scan.
    • On dev, an item forged past the old whitelist no longer jails its holder.
    • Staged disenchant still refuses an over-cap plan.
  • Phases 2–7.
    • check_loot_tables and the loot-sim tables pass first.
    • A clean repack, then bin/rebuild-and-arm.
    • Loot Lab UAT: roll every rarity at levels 1, 20, 40 and 60 against the budget; open a low-area and a high-area chest; kill a normal creature, an elite and a boss.
    • The stamps survive the party roll.
    • A gem into a forged item overwrites nothing.
    • Reforge changes only LOOT_AFX_*.
    • The bonus-roll prompt and its lockout work.
    • Wishlist bias shows across about 50 rolls.
  • Phase 8.
    • bin/wiki-golden check shows zero diff on the archive corpora.
    • Named-pool items drop out of inaccessible_items.json.
    • tests/check_customizations_hub.py passes.
